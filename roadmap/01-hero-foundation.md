# Этап 01 — Герой: XP, золото, характеристики

Связано с игровым дизайном: [`Герой`](../docs/game-design/01-hero.md).

## Цель

Сейчас герой в коде — это "пустышка": только `ID`, `Name`, `Level`. Задача этапа — довести
структуру игрока до той, что описана в дизайне (`XP`, `Gold`, характеристики), и научиться
её реально сохранять и менять в базе. Это фундамент — почти всё остальное (квесты, боссы,
магазин) будет просто менять поля этой структуры.

## Текущее состояние

`internal/models/user.go`:
```go
package models

type Player struct {
	ID    int64
	Name  string
	Level int
}
```

`internal/database/db.go`:
```go
const createTablesQuery = `
CREATE TABLE IF NOT EXISTS player (
	id BIGINT PRIMARY KEY,
	name TEXT,
	level INTEGER DEFAULT 1
);
`
```

`internal/bot/bot.go` — в `ReturnText` уже есть плейсхолдеры `XP: 0` и `Gold: 0`, но это
захардкоженный текст, а не значение из базы.

## Задачи

1. **Расширить структуру `Player`** в `internal/models/user.go`:
   ```go
   type Player struct {
       ID        int64
       Name      string
       Level     int
       XP        int
       Gold      int
       Strength  int
       Knowledge int
       Focus     int
   }
   ```

2. **Обновить схему таблицы** в `db.go`. Так как таблица уже может существовать у тебя
   локально (ты её создавал через `CREATE TABLE IF NOT EXISTS`), одного изменения
   константы недостаточно — `IF NOT EXISTS` не добавит новые колонки в уже существующую
   таблицу. Нужно либо пересоздать локальную БД (`docker compose down -v && docker compose up db`),
   либо явно добавить недостающие колонки:
   ```go
   const createTablesQuery = `
   CREATE TABLE IF NOT EXISTS player (
       id BIGINT PRIMARY KEY,
       name TEXT,
       level INTEGER DEFAULT 1,
       xp INTEGER DEFAULT 0,
       gold INTEGER DEFAULT 0,
       strength INTEGER DEFAULT 0,
       knowledge INTEGER DEFAULT 0,
       focus INTEGER DEFAULT 0
   );
   `
   ```
   Про честные миграции (когда просто ALTER TABLE в коде — уже не лучший вариант) поговорим
   на [этапе 08](08-elite-bosses-infra.md).

3. **Обновить SQL-запросы** `CreatePlayer` и `GetUserByID`, чтобы читать/писать новые поля
   (можно начать только с `xp` и `gold`, характеристики добавить следом — не обязательно
   всё сразу).

4. **Добавить методы для изменения игрока.** Вот тут будет первое настоящее знакомство с
   методами в Go:
   ```go
   func (p *Player) AddXP(amount int) {
       p.XP += amount
       for p.XP >= p.xpToNextLevel() {
           p.XP -= p.xpToNextLevel()
           p.Level++
       }
   }

   func (p *Player) xpToNextLevel() int {
       return p.Level * 1000 // любая формула, можно проще
   }
   ```
   Эти методы меняют структуру в памяти. Отдельно нужна функция в `database`, которая
   сохранит новое состояние в БД (например `UpdatePlayer(ctx, pool, player)`), потому что
   методы на структуре сами по себе ничего не знают про базу данных — это разделение
   ответственности специально, так принято в Go: модель отдельно, доступ к данным отдельно.

5. **Обновить `ReturnText` в `bot.go`**, чтобы подставлять реальные `XP` и `Gold` из
   `existPlayer`, а не нули.

## Go-концепции

**Структуры (struct)** — это способ Go сгруппировать несколько полей в один тип, как
"карточка персонажа". У структуры нет методов "из коробки", как в объектно-ориентированных
языках с классами — методы к структуре просто отдельно объявляются рядом.

**Методы и receiver.** `func (p *Player) AddXP(...)` — это метод с *receiver*'ом `p *Player`.
`*Player` (указатель на Player) означает, что метод может изменить сам объект: если бы
receiver был `Player` (без звёздочки), метод работал бы с копией структуры, и изменения
пропадали бы за пределами метода. Правило new-новичка: если метод должен что-то менять —
receiver должен быть указателем (`*Player`); если только читает — можно оставить значением
(`Player`), но для единообразия в одной структуре обычно выбирают один стиль для всех методов.

**Указатели (pointers).** `*Player` — тип "указатель на Player", `&player` — получить
указатель на существующую переменную. В Go указатели нужны в первую очередь для двух вещей:
(1) чтобы функция/метод могла изменить оригинал, а не копию, и (2) чтобы не копировать
большие структуры лишний раз. `existPlayer, err := database.GetUserByID(...)` возвращает
`Player` по значению — а вот `player.AddXP(50)` сработает, только если `existPlayer` —
адресуемая переменная (обычная локальная переменная — адресуема, так что всё в порядке).

**Нулевые значения (zero values).** В Go у каждого типа есть значение "по умолчанию":
у `int` это `0`, у `string` — `""`. Именно поэтому в дизайне игрока с нуля не нужно
дополнительно писать код "поставить XP=0" — если поле не заполнено, оно и так будет 0.
Это удобно, но следи, чтобы не спутать "поле реально равно 0" и "поле не было установлено".

## Готово, когда...

- В `Player` есть поля `XP`, `Gold` (характеристики — по желанию, можно на следующем этапе).
- В таблице `player` реально хранятся `xp` и `gold`, значения переживают перезапуск бота.
- После `/start` у существующего игрока в сообщении показываются настоящие XP и золото,
  а не захардкоженные нули.
- Есть хотя бы один метод (`AddXP` или похожий), который меняет игрока и покрыт простым
  ручным тестом — например, вызвал `/start` несколько раз и убедился, что данные не теряются.
