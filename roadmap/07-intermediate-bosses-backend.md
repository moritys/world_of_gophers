# Этап 07 — Средние боссы: backend

Связано с игровым дизайном: [`Боссы`](../docs/game-design/04-bosses.md) (раздел
"Средние боссы") и главой 🏹 **Backend-подмастерье** (HTTP, JSON, роутинг).

## Цель

Средние боссы в дизайне — Интерфейсы, Обработка ошибок, HTTP, JSON, Конкурентность,
Горутины. В отличие от начальных боссов (квиз про теорию), эти темы удобнее закрывать,
реально применяя их в самом проекте, а не только отвечая на вопросы про них.

## Текущее состояние

Проект — чисто Telegram-бот, никакого HTTP-сервера, единственное "хранилище" —
`internal/database` напрямую как конкретная реализация, без абстракции. Обработка ошибок
местами есть, но не всегда консистентная (например, `GetUserByID` печатает ошибку в
`fmt.Println` и одновременно возвращает её — стоит выбрать что-то одно, обычно возврат
ошибки выше, а печать — на самом верхнем уровне, там, где решают, что с ней делать).

## Задачи, по одной на "босса"

### 🐉 Интерфейсы

Выдели интерфейс `PlayerStore` поверх `internal/database`, чтобы `bot.HandleMessage` не
зависел напрямую от `pgxpool.Pool`:
```go
type PlayerStore interface {
    GetUserByID(ctx context.Context, id int) (models.Player, error)
    CreatePlayer(ctx context.Context, id int, name string) error
    UpdatePlayer(ctx context.Context, p models.Player) error
}
```
Зачем: это открывает дорогу к тестам с "поддельной" (in-memory) реализацией `PlayerStore`
вместо реальной БД — не нужно поднимать Postgres, чтобы протестировать логику `HandleMessage`.

### 🐉 Обработка ошибок

Пройтись по коду и привести обработку ошибок к одному стилю: функции возвращают `error`,
оборачивают его через `fmt.Errorf("...: %w", err)`, а решение "залогировать" или "ответить
пользователю" принимается в одном месте — там, где ошибка "всплывает" до вызывающего кода
верхнего уровня (в `HandleMessage` или `main`).

### 🐉 HTTP + JSON + роутинг

Добавь небольшой HTTP-сервер рядом с ботом (может работать в отдельной горутине от
поллинга Telegram) — например, для админки/статистики:
```go
mux := http.NewServeMux()
mux.HandleFunc("GET /players/{id}", handleGetPlayer)
mux.HandleFunc("GET /leaderboard", handleLeaderboard)

go http.ListenAndServe(":8080", mux)
```
(С Go 1.22+ в стандартный `net/http` завезли методы и параметры пути прямо в `ServeMux` —
отдельный роутер типа `chi` не обязателен для простого случая.) JSON-ответ:
```go
func handleGetPlayer(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
    // ... достать игрока через PlayerStore ...
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(player)
}
```

### 🐉 Конкурентность и горутины

Раз бот и HTTP-сервер теперь работают одновременно — это уже конкурентность. Плюс можно
добавить фоновую горутину, которая раз в день "закрывает" истёкшие боевые сессии с боссами
(этап 04) по таймеру:
```go
go func() {
    ticker := time.NewTicker(1 * time.Hour)
    defer ticker.Stop()
    for range ticker.C {
        cleanupStaleSessions()
    }
}()
```

## Go-концепции

**Интерфейсы.** Интерфейс в Go описывает **поведение** ("что уметь делать"), а не
"откуда наследоваться" — любой тип, у которого есть методы с нужными сигнатурами,
автоматически подходит под интерфейс, без явного `implements` как в Java/C#. Это называют
"структурная типизация" (structural typing). Именно поэтому легко подменить реальную
реализацию (`database.Store`) на тестовую (`fakeStore`) — обеим достаточно иметь одинаковые
методы.

**Горутины (`go func() { ... }()`).** Горутина — это лёгкий "поток выполнения",
управляемый рантаймом Go (не операционной системой напрямую), поэтому их можно создавать
тысячами почти бесплатно по памяти. `go` перед вызовом функции просто говорит "запусти это
не дожидаясь результата, продолжай выполнение дальше". Ключевая ловушка для новичков:
`main()` не будет ждать горутины сам по себе — если процесс завершится, недоделанные
горутины просто оборвутся. Поэтому HTTP-сервер и Telegram-поллинг в `main` должны оба
"жить" достаточно долго (например, через `select {}` в конце, или через `errgroup`, если
хочется красиво дождаться первой ошибки от любого из них).

**Каналы (channels) — коротко.** В этом этапе можно обойтись без них, но раз речь про
конкурентность: канал (`chan T`) — это типизированная "труба" для обмена данными между
горутинами, безопасная в отличие от простого доступа к общей памяти. Девиз сообщества Go:
"не общайтесь через разделяемую память, разделяйте память через общение" (общайтесь через
каналы). Если позже понадобится, например, очередь входящих Telegram-апдейтов, разбираемых
пулом воркеров — вот тут каналы и пригодятся.

**`context.Context`.** Уже используется в проекте (`ctx context.Context` почти везде) —
это механизм передачи "сигнала отмены" и дедлайнов через цепочку вызовов. В HTTP-сервере
`r.Context()` автоматически отменяется, если клиент разорвал соединение — стоит прокидывать
именно его в вызовы БД внутри HTTP-хендлеров, а не создавать `context.Background()` заново.

## Готово, когда...

- Есть интерфейс `PlayerStore`, и хотя бы одна функция/тест использует не реальную БД, а
  простую реализацию интерфейса в памяти.
- Работает HTTP-эндпоинт (`/players/{id}` или похожий), отдающий JSON.
- Бот и HTTP-сервер работают одновременно из одного процесса без взаимной блокировки.
