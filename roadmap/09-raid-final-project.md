# Этап 09 — Рейд-боссы: финальный проект

Связано с игровым дизайном: [`Боссы`](../docs/game-design/04-bosses.md) (раздел
"Рейд-боссы") и финалом главы 👑 **Кандидат на стажировку**: финальный рейд-босс —
🐲 **Собеседование на стажировку**.

## Цель

В дизайне рейд-боссы — это уже целые проекты (Telegram-бот, ToDo API, Кинотеатр API,
Магазин API, Система рекомендаций). World of Gophers сам по себе уже закрывает пункт
"Telegram-бот" — этот этап про то, чтобы довести именно его до состояния, которое не
стыдно показать на собеседовании, а не про то, чтобы стартовать новый проект с нуля.

## Текущее состояние

После этапов 01–08 у бота есть: полноценный игрок с характеристиками, квесты, ачивки,
боссы трёх уровней сложности, стрики, магазин, HTTP API, миграции, тесты. Не хватает
"полировки": документации, CI, чистого деплоя.

## Задачи

1. **README.md проекта** — переписать текущий короткий README (сейчас там только
   psql-команды) в нормальное описание: что это, как запустить, скриншот/пример диалога с
   ботом, ссылка на этот roadmap и на игровой дизайн.

2. **CI (GitHub Actions)** — простой workflow, который на каждый push прогоняет
   `go vet ./...`, `go build ./...` и `go test ./...`:
   ```yaml
   # .github/workflows/ci.yml
   name: CI
   on: [push, pull_request]
   jobs:
     test:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-go@v5
           with:
             go-version: "1.26"
         - run: go vet ./...
         - run: go build ./...
         - run: go test ./...
   ```

3. **Линтер** — `golangci-lint` локально и/или в CI, чтобы заранее ловить неиспользуемые
   переменные, неправильную обработку ошибок и т.п.

4. **Деплой на реальный сервер** — то, что уже отмечено как идея в твоих заметках
   ("bot в тг для поиска фильмов: перенести на сервер, добавить докер, добавить БД" — тот
   же путь применим и здесь): например, простой VPS + `docker compose up -d`, либо
   какая-нибудь PaaS-платформа с поддержкой Docker.

5. **Финальный рейд-босс — подготовка к собеседованию.** Не код, а рефлексия: сможешь ли
   ты объяснить вслух, почему в проекте выбраны структуры/методы там, где они выбраны,
   зачем интерфейс `PlayerStore`, как работает транзакция при покупке в магазине, почему
   мьютекс/канал нужен (или не нужен) там-то. Собеседование по Go часто спрашивает именно
   "почему так", а не "перескажи синтаксис" — и весь этот roadmap специально проведён так,
   чтобы на каждый вопрос "почему" у тебя был реальный код-пример из собственного проекта.

## Go-концепции

**`go vet`.** Статический анализатор, идущий в комплекте с самим Go — ловит
подозрительные конструкции (неправильные форматные строки в `fmt.Printf`, некоторые виды
некорректного использования конкурентности и т.п.), которые компилятор пропускает, но
которые почти всегда баг.

**`golangci-lint`.** Обёртка над десятками линтеров сразу (`gofmt`, `govet`, `staticcheck`,
`errcheck` и другие) с одной конфигурацией — стандарт де-факто в Go-сообществе для
командных и open-source проектов.

**Модули и версии (`go.mod` ещё раз).** На этом этапе полезно перечитать `go.mod` осознанно:
`require ... // indirect` — зависимости, которые тянутся не напрямую твоим кодом, а
зависимостями твоих зависимостей; `go mod tidy` подчищает список, убирая лишнее и добавляя
недостающее, исходя из того, что реально импортируется в коде.

## Готово, когда...

- README рассказывает новому человеку, что это за проект и как его запустить, без
  дополнительных вопросов.
- CI зелёный на каждом коммите в основную ветку.
- Бот развёрнут и доступен (не только `docker compose up` локально).
- Ты можешь пройтись по коду и объяснить вслух любое из решений выше — это и есть
  настоящая победа над 🐲 финальным рейд-боссом.
