# Этап 08 — Элитные боссы: инфраструктура

Связано с игровым дизайном: [`Боссы`](../docs/game-design/04-bosses.md) (раздел
"Элитные боссы") и главами ⚔️ **Хранитель данных** (SQL, PostgreSQL, миграции) и
👑 **Кандидат на стажировку** (Docker, тесты).

## Цель

Элитные боссы в дизайне — PostgreSQL, Docker, JWT, Тестирование, Redis. К этому моменту
бот уже умеет много всего игрового — этот этап про то, чтобы проект стал "поддерживаемым":
с настоящими миграциями, тестами и (опционально) кэшем/авторизацией.

## Текущее состояние

- Схема БД создаётся через один `CREATE TABLE IF NOT EXISTS` при каждом старте — рабочий
  вариант для одиночного разработчика, но не масштабируется на "накатить изменение схемы
  на прод без потери данных".
- Docker и docker-compose уже настроены и рабочие (см. `Dockerfile`, `docker-compose.yaml`).
- Тестов в проекте пока нет (`go test ./...` — пусто).
- HTTP-эндпоинт из этапа 07 (если добавлен) — без авторизации, открыт всем.

## Задачи, по одной на "босса"

### 💀 PostgreSQL — настоящие миграции

Замени ручной `createTablesQuery` на инструмент миграций, например
[`golang-migrate`](https://github.com/golang-migrate/migrate) или
[`goose`](https://github.com/pressly/goose). Идея: каждое изменение схемы — отдельный
пронумерованный файл (`0001_create_player.up.sql`, `0002_add_xp_gold.up.sql`, ...),
применяются по порядку, инструмент сам отслеживает, какие уже накатаны. Это решает проблему
с этапа 01 ("IF NOT EXISTS не добавляет колонки в существующую таблицу") по-настоящему.

### 💀 Docker

Улучшить существующий `Dockerfile`: запуск от непривилегированного пользователя вместо
root внутри контейнера, healthcheck для самого бота (не только для базы, как сейчас), и
явное закрепление версии базового образа (`golang:1.26` уже зафиксирован — хорошо; для
`debian:bookworm-slim` тоже стоит подумать про закрепление тега).

### 💀 JWT — если оставляли HTTP API на этапе 07

Простая авторизация по токену для админских эндпоинтов (`/leaderboard`, `/players/{id}`),
чтобы не быть полностью открытыми наружу. Для внутреннего проекта достаточно самого
простого варианта: сравнение статического токена в заголовке `Authorization`, без полноценной
JWT-библиотеки — настоящий JWT добавляет смысл, если появится более одного "клиента" API.

### 💀 Тестирование

Первые юнит-тесты. Начни с чистой логики без побочных эффектов — она проще всего
тестируется:
```go
func TestUpdateStreak(t *testing.T) {
    tests := []struct {
        name   string
        last   time.Time
        now    time.Time
        streak int
        want   int
    }{
        {"тот же день", day(1), day(1, 5), 3, 3},
        {"следующий день", day(1), day(2), 3, 4},
        {"пропуск дня", day(1), day(5), 3, 1},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := UpdateStreak(tt.last, tt.now, tt.streak)
            if got != tt.want {
                t.Errorf("UpdateStreak() = %d, want %d", got, tt.want)
            }
        })
    }
}
```
Для функций, которым нужна БД (`database.CreatePlayer` и т.п.), после интерфейса
`PlayerStore` из этапа 07 можно тестировать `bot.HandleMessage` с поддельной реализацией,
не поднимая Postgres. Для тестов, которым реально нужна настоящая БД (например, проверить
сам SQL-запрос) — есть `testcontainers-go`, который поднимает Postgres в Docker прямо во
время `go test`.

### 💀 Redis — опционально

Кэш для `/leaderboard` (топ игроков по XP), чтобы не считать `ORDER BY xp DESC LIMIT 10`
на каждый запрос — обновлять кэш раз в минуту фоновой горутиной (см. этап 07 про горутины
по таймеру).

## Go-концепции

**Табличные тесты (table-driven tests).** Пример выше — стандартная для Go идиома: вместо
множества похожих отдельных тестовых функций — один срез случаев (`tests := []struct{...}`)
и один цикл `for _, tt := range tests`, внутри которого `t.Run(tt.name, ...)` создаёт
именованный подтест. `go test -run TestUpdateStreak/пропуск_дня` позволяет запустить
конкретный случай отдельно.

**Пакет `testing`.** Функция теста имеет сигнатуру `func TestXxx(t *testing.T)`, где `Xxx` —
с заглавной буквы. `t.Errorf` помечает тест как проваленный, но продолжает выполнение (в
отличие от `t.Fatalf`, который сразу прерывает текущий тест). Запуск: `go test ./...`
из корня модуля прогонит все тесты во всех пакетах.

**Моки через интерфейсы.** Раз в этапе 07 появился интерфейс `PlayerStore` — "поддельная"
реализация для тестов — это просто ещё одна структура с теми же методами, только хранящая
данные в `map` в памяти вместо похода в Postgres:
```go
type fakeStore struct {
    players map[int]models.Player
}

func (f *fakeStore) GetUserByID(ctx context.Context, id int) (models.Player, error) {
    p, ok := f.players[id]
    if !ok {
        return models.Player{}, errors.New("not found")
    }
    return p, nil
}
```

## Готово, когда...

- Схема БД управляется файлами миграций, а не одной константой в коде.
- `go test ./...` реально что-то проверяет и проходит.
- Dockerfile обновлён (непривилегированный пользователь как минимум).
- (Опционально) HTTP-эндпоинты защищены токеном, есть кэш для лидерборда.
