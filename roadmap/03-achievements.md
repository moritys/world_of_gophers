# Этап 03 — Достижения

Связано с игровым дизайном: [`Достижения`](../docs/game-design/03-achievements.md).

## Цель

Разовые ачивки, которые выдаются по событию (первый коммит, 7 дней подряд и т.д.), в
отличие от квестов — их нельзя "сделать" по команде, они выдаются автоматически, когда
выполняется условие.

## Текущее состояние

После этапов 01–02 у игрока есть XP, золото и учёт выполненных квестов. Системы проверки
условий и хранения "у игрока есть такая-то ачивка" пока нет.

## Задачи

1. **Тип `Achievement`**:
   ```go
   type Achievement struct {
       ID   int
       Name string
       XP   int
   }
   ```

2. **Таблица `player_achievement (player_id, achievement_id, unlocked_at)`** — связь
   игрока и полученных ачивок (классическая связь "многие ко многим" через отдельную
   таблицу).

3. **Каталог ачивок** — как и с квестами, для начала можно прямо в коде:
   ```go
   var Achievements = []Achievement{
       {ID: 1, Name: "Первый коммит", XP: 10},
       {ID: 2, Name: "7 дней подряд", XP: 50},
       {ID: 3, Name: "Первый REST API", XP: 100},
   }
   ```

4. **Функция проверки** — вызывается после ключевых событий (выполнение квеста, победа
   над боссом, обновление стрика):
   ```go
   func CheckAchievements(ctx context.Context, pool *pgxpool.Pool, playerID int, event Event) error {
       // например: если event.Type == "quest_done" && event.QuestID == 1 → выдать "Первый коммит"
   }
   ```
   Пока событий немного, простого `switch` по типу события достаточно. Когда логика
   разрастётся — можно вынести в отдельные функции-проверки по одной на ачивку.

5. **Не выдавать одну и ту же ачивку дважды** — перед вставкой в `player_achievement`
   проверять, нет ли её уже (`ON CONFLICT DO NOTHING` в SQL — удобный способ сделать это
   атомарно одним запросом, без гонки условий).

## Go-концепции

**Свой тип "событие" (Event).** Это первый шаг к тому, чтобы разные части бота (квесты,
боссы, стрики) не были жёстко переплетены друг с другом, а сообщали "что-то произошло",
а достижения сами решали, реагировать или нет:
```go
type Event struct {
    Type     string // "quest_done", "boss_defeated", "streak_updated"
    PlayerID int
    Payload  int // например, ID квеста/босса
}
```
Здесь `Type string` — не самый строгий вариант (можно опечататься в строке), но для
небольшого проекта это нормально. Более строгий вариант — использовать `iota` и
именованные константы (см. ниже) или, ещё дальше, интерфейсы (см.
[этап 07](07-intermediate-bosses-backend.md)).

**`iota`.** Если типов событий немного и они не будут меняться на лету, можно объявить их
как перечисление:
```go
type EventType int

const (
    EventQuestDone EventType = iota
    EventBossDefeated
    EventStreakUpdated
)
```
`iota` — это счётчик, который Go автоматически увеличивает на 1 в каждой следующей строке
внутри `const (...)`, начиная с 0. Так получаются простые "enum"-подобные константы без
явного проставления чисел руками.

**`ON CONFLICT DO NOTHING` / `ON CONFLICT ... DO UPDATE`.** Это не Go, а SQL-фича
PostgreSQL, но она напрямую влияет на то, как выглядит Go-код: вместо "сначала SELECT,
проверить, потом INSERT" (что подвержено гонке при параллельных запросах) — один запрос,
который сам решает конфликт. Меньше кода, меньше багов.

## Готово, когда...

- Есть таблица `player_achievement` и функция для выдачи ачивки конкретному игроку.
- Хотя бы одна ачивка реально выдаётся автоматически по событию (например, за первый
  выполненный квест), без ручной команды.
- Повторное срабатывание условия не создаёт вторую такую же запись об ачивке.
- Команда типа `/achievements` показывает игроку, что уже получено.
